## Ranked Performance Leads

1. Measure current-tree attention stages, then extend shared matrix machinery
   before adding another family-specific kernel. The current F32 value-matrix
   call selects scalar grouped arithmetic; the generic MMA eligibility in
   `metal/latent.rs` is Q6_K-only. Multi-query attention is another candidate,
   but a 256-row chunk exceeds the 128-row raw ring: blindly writing all keys
   first would destroy history needed by early queries.
2. Measure routed-expert occupancy. With six routes and 272 experts, 256 prompt
   rows average 5.65 assignments per expert, versus 16 gate/up and 32 down tile
   slots. Actual skew, occupied tiles and weight traffic must decide between
   smaller tiles and larger memory-admitted chunks.
3. Measure residual per-row projected RMS and per-group output packing/calls.
   These are lower-risk sharing opportunities, not evidence of a 4.2x saving.

The older 1K profile attributed 9.84 GPU seconds to attention and 3.29 to FFN.
It predates the last optimizations and cannot attribute the final checkpoint.
Mixed precision is a separate arithmetic-contract decision, not a silent way
to reuse F16 primitives under a NativeF32 label.

C's continuation ends at EOS after 77 generated tokens with `incomplete V4.1
tool call`, not at the 256-token output ceiling. The response exposes no raw
pending call, so model-output versus parser cause is not established. No return
to A was executed, and no successful end-to-end session is claimed. The owned
server tears down cleanly; the parser remains fail-closed.

The completed requests expose a concrete cache-scheduling omission: changing
the user task loses the 11K shared system/tool prelude. At baseline, the renderer
provides only a conversation-end boundary, and V4.1 captures only that cut.
A bounded fix is implemented but not yet measured: derive the shared prelude
with the same official renderer, verify byte and token prefix equality, and
capture it through the existing SnapshotCache alongside the existing
conversation-end checkpoint.
This is not a new cache stack or an attention arithmetic rewrite.

cx Sol reviewed this reuse choice in session
`01a15367-51e5-76f0-bf48-83233f6a8362`: no generic boundary-to-token helper exists;
GLM's private `cut_positions` is coupled to its schedules. A small local
adaptation of the same verified-prefix logic is appropriate. The official
renderer has no public boundary metadata, so rendering and verifying the
prelude avoids copying its template or searching user content for markers.
The review also identified that optional snapshot capture must preserve the
caller's outstanding output-memory reserve. Capture now checks the full CPU
entry, forward bookkeeping and caller reserve with shared process-headroom
admission. Denial skips only the optional copy and preserves execution cuts
and older entries; CPU reserve is not charged to Metal. Request-state admission
and the existing forward snapshot admission are unchanged.

Focused verification passes 57 V4.1 CLI tests with required Metal/API validation
(one existing real-model witness remains opt-in). Real cache-scheduling latency
and exact-tree full suites remain pending for this fix. cx Luna's pre-checkpoint
review (`01a15373-2f81-7c80-b070-6b81522d9a7d`) finds no blocking source or test
issues; it does not establish an unmeasured speedup.
