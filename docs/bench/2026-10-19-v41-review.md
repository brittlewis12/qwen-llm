## Reuse Map

The mapping was reviewed with cx Sol, session
`01a1531c-8da5-7e90-8d1c-b59e690b3761`. This is not evidence that DS4 is faster.

| Operation | Current reuse and relevant implementation | Boundary that must remain explicit |
| --- | --- | --- |
| Index scoring | V4.1 `attention_gpu::Workspace::encode_inner` and `kernel_deepseek_v41_attention_index_heads`; DS4 calls shared `metal::sparse::encode_lightning_scores_f16_matrix`. | Existing shared operands are F16; V4.1 is F32. | Selection | V4.1 tiled total-order sort; shared selector is in `metal/sparse.rs`. | Shared zero/subnormal and nonfinite policy differs: V4.1 uses masked negative infinity, forced-last positive infinity and signed-zero ordering. Do not substitute it unchanged. |
| Sink attention | V4.1 `sink_passes`/`ValueMatrix`; DS4 dense/selected sink wrappers and shared selected-attention primitives are in `deepseek_v4_metal/indexer.rs` and `metal/sparse.rs`. | Share a numerical primitive, not the scheduler/cache layout. | Compressor | Projection machinery is shared; V4.1 pooling is ratio 1/2. DS4 frontier/pool/roll helpers are in `deepseek_v4_metal/indexer.rs`. | DS4 ratio 4/128 frontier geometry, V4.1 pair phase, pending values/gates, cross-layer ownership and group-start RoPE are not the same state machine. |

At this source checkpoint, F32 value matrices select scalar grouped arithmetic;
generic MMA eligibility is Q6_K-only. A 256-row chunk exceeds the 128-row raw
ring, so writing all keys first would destroy early-query history. Six routes
over 272 experts and 256 rows average 5.65 assignments per expert versus 16
gate/up and 32 down slots; this is not measured occupancy or a speedup estimate.

The older 1K profile attributed 9.84 GPU seconds to attention and 3.29 to FFN.
It predates the last optimizations and cannot attribute the final checkpoint.
Mixed precision is a separate arithmetic-contract decision, not a silent way
to reuse F16 primitives under a NativeF32 label.

## Agent Latency Measurement

Measurements use `scripts/reference/glm53/serve_agent_reuse_screen.py` and its
system/tool fixture. First delta, visible answer, completed tool availability
and whole-request time are distinct; cached requests are not cold throughput.

### Baseline Agent Screen

The unmodified shared screen uses the retained OpenCode instructions and 12
tool schemas, synthetic tool results, non-thinking mode, a 256-output-token
ceiling and two tool continuations per task. Evidence: `agent-1/` on `733d629f`.
The planned three repetitions stopped after the first failed screen; these are
single-request observations, not three-repetition latency statistics.

| Request | Reused / new tokens | First delta (s) | Completed tool available (s) | Result |
| --- | --- | ---: | ---: | --- |
| A cold | 0 / 11,479 | 150.199 | 154.597 | completed |
| A tool continuation | 11,578 / 148 | 4.247 | 4.247 | completed |
| A answer continuation | 11,769 / 89 | 1.511 | n/a | completed |
| B changed user task | 0 / 11,480 | 109.079 | 113.479 | completed |
| B continuation | 11,582 / 197 | 2.874 | n/a | completed |
| C new task | 0 / 11,472 | 108.918 | 110.975 | completed |
| C continuation | live hit / 77 | no delta | no tool | failed |

C's continuation ends at EOS after 77 generated tokens with `incomplete V4.1
tool call`, not at the 256-token output ceiling. The response exposes no raw
pending call, so model-output versus parser cause is not established. No return
to A was executed, and no successful end-to-end session is claimed. The owned
server tears down cleanly; the parser remains fail-closed.

The completed requests expose a concrete cache-scheduling omission: changing
the user task loses the 11K shared system/tool prelude. At baseline, the renderer
provides only a conversation-end boundary, and V4.1 captures only that cut.
A bounded fix is implemented in `fbd5770c`: derive the shared prelude
with the same official renderer, verify byte and token prefix equality, and
capture it through the existing SnapshotCache alongside the existing
conversation-end checkpoint.
This is not a new cache stack or an attention arithmetic rewrite.

cx Sol reviewed this reuse choice in session
`01a15367-51e5-76f0-bf48-83233f6a8362`: no generic boundary-to-token helper exists;
GLM's private `cut_positions` is coupled to its schedules. A small local
adaptation of the same verified-prefix logic is appropriate. The official
renderer has no public boundary metadata, so rendering and verifying the
prelude avoids copying its template or searching user content for markers.
The review also identified that optional snapshot capture must preserve the
caller's outstanding output-memory reserve. Capture now checks the full CPU
entry, forward bookkeeping and caller reserve with shared process-headroom
admission. Denial skips only the optional copy and preserves execution cuts
and older entries; CPU reserve is not charged to Metal. Request-state admission
and the existing forward snapshot admission are unchanged.

Focused verification passes 57 V4.1 CLI tests with required Metal/API validation
(one existing real-model witness remains opt-in). cx Luna's pre-checkpoint
review (`01a15373-2f81-7c80-b070-6b81522d9a7d`) finds no blocking source or test
issues. On committed `fbd5770c`, contracts pass with 119 required V4.1 tests and
zero skips; the full serial release workspace passes 3,047 tests, zero failures,
and 647 explicit ignores. Both checks require Metal and enable API validation.

These listed first deltas are visible answer text; tool-only continuation
requests can emit their first delta only when the completed call is available.
B and C restore from `snapshot_ram` in 18.6-20.9 ms. Their newly evaluated
prefill costs 520.0-521.7 ms and 424.2-424.8 ms respectively. Return-to-A also
uses RAM snapshots; its suffix differs with generated history. One tool-history
rerender falls back from live continuation to a longer transcript snapshot,
evaluating 357 rather than all 11,835 tokens in 3.915 seconds.

The baseline B miss was 109.079 seconds to first delta and 109.025 seconds of
prefill. The post-fix 0.588-second result demonstrates shared-prefix reuse, not
faster cold attention or a 500 tokens/s engine. The cold 11,479-token first turn
still takes 113.6-124.0 seconds to first text, excluding server/model startup.
Do not attribute its difference from the single 150.2-second baseline cold
observation to this fix; OS caches, warmup and scheduling are not controlled
as a paired cold-start experiment.

Two bounded conversations exhaust the two-tool-step budget with calls pending
(repetition 1 C, repetition 3 A). This is not a task-quality success claim.
The baseline incomplete-call failure did not recur in these three screens;
its cause remains unestablished and no parser fix is claimed.

There is also a real tail-latency outlier: repetition 1 C3 evaluates 270 new
tokens in 20.025 seconds and exposes its completed tool at 23.019 seconds.
The other two C3 turns evaluate 270 tokens in 2.866/2.876 seconds. These are
different generated histories, not a controlled replay; the slow sample is
retained and not attributed to a kernel, IO, or cache mechanism without profiling.
