# V4.1 three-agent append TTFT: queue exposure and service quanta

**Scheduling explains the large short-append tails; native prefill still dominates the median, especially for ~1K appends.** The radix pair-1 short/1K TTFT reversal matches two reversals of native-call order. No kernel regression is needed to explain it. This is a records-only analysis of existing runs, with no GPU work, model load, or product changes. It does not relabel any previous failed gate.

The largest measured opportunity is bounding service ahead of a waiting short append, not increasing admission capacity. A costless 200–500 ms bound on observed peer service prices about **340–640 ms off radix short p95**. That is an optimistic opportunity bound, not a measured policy gain. Short-first service can move delay onto ~1K requests; pair 1 demonstrates that cost directly. The recommendation is a **row-preserving, conditional inter-request prefill yield** with ready-job admission, starting with the small timing additions below. A blind `PREFILL_FAIR=0` toggle changes numerical geometry and is not an equivalent implementation.

## Inputs, populations and coverage

19 retained arms, 164 files / 73,627,021 input bytes verified against SHA256: six purged greedy attention-bundle arms, six purged greedy compact/radix arms, six purged Engram row-cache arms, and one extra Engram diagnostic arm. The diagnostic arm is retained separately and never pooled into paired cohorts. [Input manifest](2026-11-14-v41-serve-ttft/input-manifest.json) contains original M5 paths and digests. The Engram arms used **agent-default sampling**, seed20261109, 180 s windows and 8-token root warm replies. Attention/radix used **greedy** sampling, seed20261112, 120 s windows and 32-token warm replies. The cohorts also differ in source version and short-append header folding: all 82 primary Engram short calls use two native calls; all 54 attention and 105 radix short calls use one. Their distributions are shown separately, not as a causal cross-campaign A/B.

Classes use **actual `new` rows**, not the requested suffix: short is1–511; ~1K is512–2,000. For example, a requested497-row suffix becomes553 new rows and belongs to the latter class. Primary append quantiles retain completed calls offered and first-visible inside the window. Carry-in, unfinished and censored calls remain in the [full derived ledger](2026-11-14-v41-serve-ttft/calls.jsonl); they are not assigned a fabricated native cost or actual new-row class. All 375 primary short/~1K calls in the three paired cohorts join uniquely to native prefill profiles by request extent and interval. Roots are analyzed separately: later roots share the static prelude, but still prefill about49K new rows.

All first deltas in the primary append cohorts are `response.output_text.delta`. Results do not establish latency for first-visible tool-call arguments or other output forms. Per-arm quantiles, p99/maxima and controls are in [summary.json](2026-11-14-v41-serve-ttft/summary.json). Marginal cohorts retain every eligible call; they need not have the same count as the earlier matched-label A/B reduction.

## What the four requested components actually log

| Requested component | Available measurement | Missing boundary |
|---|---|---|
| Admission / queue | `phases.batch.queue_ms`: scheduler submit to admission, usually a few microseconds | TCP admission, HTTP upload/parse/tokenize, prepared-job mailbox wait before scheduler submit |
| Server prefill compute | `phases.prefill_ms`: accumulated native engine-call wall, excluding inter-call service; per-native GPU command spans and Engram API prices | Pure ALU time versus memory/driver stalls; CED native profiles for most root work |
| First-token work | The cursor already collects selection / ready / callback milliseconds, but V4.1 does not export them | Separate first-token CPU work and first-visible protocol emission |
| Transport | Client send and first nonempty visible delta timestamps | Header timestamp is collected but discarded; server first-visible enqueue and socket flush timestamps are absent |

Thus a fully identified four-way additive decomposition is **not recoverable** from these files. No missing component is reported as zero. The exact observable accounting is client TTFT = native prefill wall + everything outside it. The logged queue is only a small subset of the latter. Profile receipt timestamps give the additional temporal partition below, with millisecond-scale log/serialization uncertainty. Quantiles of components do not add to a quantile of their sum.

## What each call was exposed to

Native prefill intervals are reconstructed as `[log_receipt - native_wall, log_receipt]`. A peer interval intersecting a request’s before/between/after path is **exposure**, not an exact claim that all the interval was blocked queue time: input preparation may run concurrently, and request-ready timestamps are absent. The single GPU-feeding thread cannot run the waiting request’s native work during the peer’s synchronous native call. Per-profile interval/request matches and costs are retained in [native-profiles.json](2026-11-14-v41-serve-ttft/native-profiles.json).

## Scheduling levers ranked by the opportunity in these records

The exposure-cap prices optimistically clip *total observed peer service ahead of the request* with no cost for deferred peers, context switching or less efficient chunks. They are not simulations of a particular row cap, and they do not guarantee ~1K non-regression. [Counterfactual prices](2026-11-14-v41-serve-ttft/opportunity.json).

### Recommended measured stage

**Conditional, row-preserving inter-request prefill yielding**, with a ready-job feed, is the worthwhile tail experiment. First add the compact trace described below; then prove a paused1K prefill can service a250-row append at a completed layer boundary and resume with identical logits/state/next logits. Keep4K native row selection and the within-request operation order. Source `new_chunk_scratch` is per state/call, which is a useful starting point; paused-request reserves must still count during admission and three48K sessions must fit.

Existing `LAYER_SLICE_MS` callbacks only service decoders; they do not poll new HTTP work or switch to another prefilling request. Simply turning that knob on is not this candidate. The HTTP prepared-job feed and prefilling-context handoff are real engineering work. Start with a200–400ms service target only when another appender is ready; a layer/native I/O boundary can overshoot, so trace actual quanta. No kernel or row-partition change should be needed. Require bitwise witness, then the same purged nice0 interleaved3-agent cells with p50/p95 by actual new-row class, root/TPS/ITL guardrails and memory accounting. The lead must freeze the latency tradeoff criterion before the campaign: strict short-first can reproduce the very ~1K TTFT regression seen in pair1.

This recommendation targets short tails. It is not evidence that scheduling dominates most ~1K appends: current radix median per-call native fraction is91%, versus78% short, and uncontended roots spend about99.7% in prefill. Luna’s BF16 index-MMA bound remains relevant to median native work.

## Smallest useful logging addition (proposal only)

1. **Persist already collected client data:** include `headers` and response ID in `calls.jsonl`; retain warm rows in `warm-calls.jsonl` with send/header/first/end rather than only stdout TTFT. This separates client-to-headers from the remaining path and fixes root coverage without a new timer.
2. **Carry one request ID and a few existing/new instants:** accept, prepared/enqueued, worker dequeue, scheduler admission, native first/last, prefill complete. Start the queue clock before the mailbox, not only in `Scheduler::submit`. Log phase deltas using one monotonic clock and a wall/monotonic anchor for matching the local client.
3. **Export existing decode measurements:** `GenerationResult.first_token_selection_ms`, `first_token_ready_ms`, and `first_token_callback_ms` are already collected but dropped by V4.1 outcome stats. The callback is raw model bytes, not necessarily a visible protocol delta. Add first nonempty visible-delta enqueue and first socket-flush instants; only then can first-token work and response transport be separately priced.
4. **Keep causal work labels cheap:** one round ID, batch width/member IDs and start/end per native prefill or decode quantum, with the whole-process I/O delta once per batch. Emit a compact first-visible trace before generation completes so cancelled-at-window-end calls retain TTFT phases. Tag Engram host preparation if exclusive I/O time is needed; extend the wrapper to CED only for the root question.

No prompt text, token payload or additional per-kernel logging is required. CPU request preparation may overlap GPU service, so the trace should preserve overlap rather than forcing every clock interval into a mutually exclusive queue label.
